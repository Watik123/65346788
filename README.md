# Справжні знижки

Сервіс-агрегатор, що показує товари, які **реально** подешевшали: ціна нижча за типову
ціну ринку за останні 30–60 днів, а не за закреслену ціну магазину.

Статус: **етапи 5–6**: щоденний збір справжніх цін із восьми магазинів (KTC, Foxtrot, MOYO, Цитрус, Ябко,
Vencon, Artline, TTT) на GitHub Actions;
один і той самий товар з різних магазинів зіставляється автоматично (штрихкод, код моделі), сумнівні пари
відкладаються на ручну перевірку.

## Що потрібно

- Node.js 22 або новіший (`node -v`)

## Швидкий старт

```bash
npm install          # ставить залежності й генерує Prisma-клієнт
npm run db:setup     # створює базу data/app.db і наповнює її тестовими даними
npm run dev          # запускає API (порт 3001) і сайт (http://localhost:5173)
npm test             # усі тести
```

Файл `.env` необов'язковий: без нього база лежить у `data/app.db`. Зразок — `.env.example`.

## API

Запуск: `npm run dev:api`, далі `http://127.0.0.1:3001/api/...`. Порт і адресу змінюють змінні
`PORT` і `HOST`. Типи всіх відповідей лежать у `packages/shared/src/api.ts`.

| Адреса | Що віддає |
|---|---|
| `GET /api/health` | `{"status":"ok"}` |
| `GET /api/filters` | категорії (дерево з кількістю знижок), магазини, межі цін, варіанти сортування |
| `GET /api/feed` | стрічка справжніх знижок з фільтрами, сортуванням і пагінацією |
| `GET /api/products/:id` | сторінка товару: знижка з поясненням, пропозиції магазинів, історія цін за 90 діб |
| `GET /api/compare` | товари, що є в 2+ магазинах: ціни магазинів, різниця, «знижка на папері» |

Параметри `/api/feed` (усі необов'язкові):

| Параметр | Значення |
|---|---|
| `category` | slug категорії; батьківська включає підкатегорії (`elektronika`) |
| `shop` | slug магазину або кілька через кому (`alfa,delta`): товари, що є в них у наявності |
| `minDiscount` | мінімальна знижка, % |
| `minPrice`, `maxPrice` | межі найкращої ціни, ₴ |
| `minRating` | мінімальна оцінка, 0–5 |
| `sort` | `score` (за замовчуванням), `discount`, `price`, `popularity` |
| `order` | `asc` або `desc`; без нього береться природний (ціна ↑, решта ↓) |
| `page`, `limit` | сторінка (з 1) і розмір (до 60, за замовчуванням 24) |

Приклад: `/api/feed?category=smartfony&minDiscount=15&sort=price`.

Параметри `/api/compare`: `category`, `sort` (`spread` — найбільша різниця цін, за замовчуванням; `paper`,
`shops`, `price`), `paper=1` (лише «знижки на папері»), `page`, `limit`. «Знижка на папері» означає, що магазин
показує закреслену ціну зі знижкою від 10%, а інший магазин продає той самий товар за ту саму або нижчу ціну
без знижки. Для цього не потрібна історія цін, тож розділ працює з першого дня збору.
Помилки мають єдиний вигляд: `{"error":{"code":"...","message":"..."}}`.
Історія для графіків рахується від останньої доби з даними, а не від годинника.

## Сайт

React 19, React Router, TanStack Query, Tailwind CSS 4, шрифт Onest (повна кирилиця, українські літери,
знак ₴). Мова інтерфейсу українська, макет від телефона, світла й темна тема (за системою або вручну).

- **Стрічка** (`/`): картки справжніх знижок, фільтри (категорія, магазин, знижка, ціна, оцінка), сортування,
  сторінки. Усі фільтри живуть у посиланні, тож стрічку можна надіслати іншій людині.
- **Товар** (`/product/:id`): пояснення рішення, графік історії ціни 30/60/90 днів (ціни окремих магазинів
  вмикаються кнопками), таблиця пропозицій, дані графіка таблицею.
- **Порівняння цін** (`/compare`): той самий товар у різних магазинах сьогодні, де дешевше і де «знижка на
  папері». Працює, поки історії цін замало для висновків у стрічці.
- **Відсіяні** (`/rejected`): знижки, які магазини показують, але ми не підтвердили, з порівнянням
  «обіцяє магазин / насправді».

**Графіки.** Історія ціни: Recharts. Він декларативний, добре працює з темною темою через CSS-змінні й дає
готові підказки та адаптивність. Міні-графіки на картках це власний легкий SVG: десятки екземплярів Recharts у
стрічці були б зайвим навантаженням. Кольори ліній магазинів перевірені скриптом на розрізнення
в обох темах, у тому числі при порушеннях кольорового зору.

**Без сервера.** `npm run site:build` збирає базу з `datastore/` у тимчасовий файл і робить сайт, якому не
потрібен API: сторінку `apps/web/dist-site/fragment.html` (скрипти й стилі всередині) і дані поруч,
`data/index.json` (стрічка, фільтри, порівняння) та 64 файли `data/p/<n>.json` зі сторінками товарів. Сторінка
довантажує файл товару, лише коли його відкривають, тож вона не росте з історією цін. Історія в цих файлах
стиснута (ціни по днях масивом). Логіка фільтрів і сортування спільна з сервером (`packages/shared/src`), а тест
у `apps/api/src/api.test.ts` перевіряє, що вона дає ті самі відповіді, що й база.

Опублікований сайт оновлюється щодня: після збору цін (08:17 за Києвом) завдання за розкладом у Claude
запускає `npm run site:build` і публікує результат за тим самим посиланням.

## Збір цін

Каркас у `apps/api/src/scraping` робить усе, крім знань про конкретний сайт:

- **Ввічливість за побудовою.** Завантажувач читає `robots.txt` і не заходить на заборонені адреси; тримає
  паузу між запитами (за замовчуванням 1,5 с з розкидом) і поважає `Crawl-delay`; повторює невдалі запити
  з наростаючою затримкою і `Retry-After`; не йде за перенаправленням на інший домен.
- **Чесне представлення.** У `User-Agent` вказано назву робота й контакт (`SCRAPER_CONTACT` у `.env`).
  Якщо сайт блокує таке представлення, ми не маскуємось під браузер, а домовляємось з магазином.
- **Кеш і сирі відповіді.** Вдалі відповіді кешуються на 12 годин (`data/cache/<магазин>`), сирі сторінки
  зберігаються за датою для налагодження (`data/raw/<магазин>/<дата>`).
- **Журнал.** Кожен запуск це рядок у `ScrapeRun`, кожна помилка це рядок у `ScrapeError` (тип, адреса, текст).
- **Захист даних.** Різкий стрибок ціни (більш ніж у 5 разів) не записується, а потрапляє в журнал. Якщо сайт
  відмовляє 8 разів поспіль, запуск зупиняється, щоб не довбати сайт, який нас не пускає.
- **Дані зі сторінок.** Спершу розмітка schema.org (JSON-LD), потім мета-теги. Бренд не вгадується: немає в
  розмітці, то товар пропускається, якщо модуль магазину не підказав, як його визначити.
- **Лише власні товари.** Продавця з розмітки порівнюємо зі списком власних назв магазину; чужі пропускаються.

Запуск: `npm run scrape -- <магазин> --max=5 --dry-run` (пробний, нічого не пише в базу), далі без `--dry-run`.
Реальні дані краще збирати в окрему базу (`DATABASE_URL` у `.env`), а не в ту, де лежать тестові.

### Як додати магазин

Створіть `apps/api/src/scrapers/<slug>.ts` і додайте його в `src/scrapers/index.ts`:

```ts
import { parseProductPage } from '../scraping/from-schema-org'
import { sitemapUrls } from '../scraping/sitemap'
import type { ShopScraper } from '../scraping/types'

export const myShop: ShopScraper = {
  slug: 'my-shop',
  name: 'Мій магазин',
  baseUrl: 'https://shop.example',
  // Де шукати сторінки товарів (sitemap) і до якої нашої категорії вони належать
  async *discover(ctx) {
    for await (const url of sitemapUrls(ctx.fetcher, 'https://shop.example/sitemap-products.xml')) {
      yield { url, categorySlug: 'televizory' }
    }
  },
  // Як читати сторінку; для більшості магазинів вистачає розмітки schema.org
  parse: (html, ref) => parseProductPage(html, ref, { ownSellerNames: ['Мій магазин'] }),
}
```

### Один товар у різних магазинах

Під час запису товару з нового магазину шукаємо той самий серед уже відомих: спершу за штрихкодом,
потім за брендом і кодом моделі (`UE55M70HAUXUA`, `SM-S948BZKGEUC`). Різна пам'ять, колір, діагональ,
рік, модифікація (Pro, Ultra, FE…) чи комплект означають різні товари, навіть якщо назви схожі.
Сумнівні пари (код збігся лише частково, назви дуже схожі) автоматика не з'єднує, а відкладає:
`npm run match:review` показує їх, `--approve=№` з'єднує, `--reject=№` позначає як різні.
Рішення записуються в `datastore/match-decisions.jsonl` і застосовуються при кожній перебудові бази.

## Як рахується знижка

Базою порівняння береться **типова ціна ринку** за 60 діб (медіана найкращої ціни по всіх
магазинах), а не закреслена ціна магазину. Знижка **справжня**, якщо одночасно:

1. вона не менша за 5%;
2. історії цін достатньо (від 14 діб), інакше статус «замало даних»;
3. ціна не стрибала вгору-вниз (4 і більше різких змін за 30 діб = нестабільно);
4. ціна зараз «на дні»: не вища за мінімум останніх 60 діб більш ніж на 3%.

**Фейкова** знижка — та, що її бачить покупець, але вона зникає порівняно з типовою ціною:
ціну нещодавно підняли й «знизили» назад, ціна стрибає, або магазин показує закреслену
ціну, якої ринок не підтверджує.

Скор = знижка (%) × якість × популярність. Якість — оцінка зі згладжуванням (5.0 з двома
відгуками не обганяє 4.7 з 800). Популярність — `log(1 + кількість магазинів)`.
Для кожного рішення зберігаються причини українською, їх показуватиме сторінка товару.
Усі числа лежать в одному файлі: `apps/api/src/scoring/config.ts`.

## Тестові дані

54 товари в 6 категоріях, 6 магазинів, 90 діб історії цін. Бренди й моделі реальні,
**ціни, оцінки, відгуки й наявність вигадані**, посилання ведуть на `example.com`,
штрихкоди з префіксом 200 (службовий діапазон, не збігаються з реальними).
Не публікувати як справжні дані.

У кожного товару закладений сценарій цінової історії, за яким перевірятиметься скор:

| Сценарій | Кількість | Що визначає скор |
|---|---|---|
| справжня знижка (ціна впала на 11–22%) | 17 | справжня |
| фейковий підйом (ціну підняли й «знизили» назад) | 7 | фейкова: магазин обіцяє 14–21%, а знижки немає |
| нестабільна історія (ціна стрибає) | 3 | фейкова |
| повільне здешевлення | 6 | без знижки (2–4%, менше за поріг) |
| стабільна ціна | 13 | без знижки |
| стабільна ціна, але магазин постійно показує «акцію» | 5 | фейкова |
| новий товар (історія 7–11 діб) | 3 | замало даних |

## PostgreSQL

Схема не використовує `enum`, `Json`, `Decimal` і сирий SQL, тож перехід зводиться до
заміни `provider` у `schema.prisma`, адаптера в `src/lib/db.ts` і повторної міграції.
Це ще не перевірено на реальному PostgreSQL.
